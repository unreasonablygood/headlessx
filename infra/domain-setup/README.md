# HeadlessX Domain Setup

This directory is the production domain layer for HeadlessX.

It is designed for:

- Docker-based production deployments
- a dedicated Basic-Auth-protected dashboard domain
- a dedicated API domain that keeps normal `x-api-key` admission
- automatic HTTPS through Caddy

## Production Host Requirements

| Item | Minimum | Recommended |
| --- | --- | --- |
| OS | Linux server | Ubuntu 22.04+/24.04 or Debian 12 |
| CPU | 2 vCPU | 4+ vCPU |
| RAM | 8 GB | 16+ GB |
| Disk | 20 GB SSD | 40+ GB SSD |
| Network | public server IP and outbound internet | stable bandwidth with low packet loss |

Required on the host:

- Docker Engine
- Docker Compose v2
- DNS access for your dashboard and API domains
- ports `80` and `443` open to the internet
- an email address for Caddy certificate management

This setup is additive. It does not replace the current `headlessx` API/operator commands. The lifecycle side is intended to work alongside commands like:

- `headlessx scrape`
- `headlessx map`
- `headlessx crawl`
- `headlessx google`
- `headlessx tavily`
- `headlessx exa`
- `headlessx youtube`

## Purpose

The core HeadlessX stack already runs with Docker under:

```text
infra/docker/
```

This directory adds the production reverse-proxy/domain layer on top of that stack.

The intended production shape is:

- the core HeadlessX stack bound to `127.0.0.1` on the host
- Caddy joined to the same Docker network
- a password-protected dashboard domain
- an API domain whose ordinary non-health routes require `x-api-key`

Example:

- `dashboard.example.com`
- `api.example.com`

## Files

- `.env.example`
- `docker-compose.yml`
- `Caddyfile.template`
- generated by the CLI in production mode:
  - `~/.headlessx/repo/infra/docker/secrets` — private app-stack credential sources
  - `~/.headlessx/repo/infra/docker/.env` — non-secret core configuration
  - `~/.headlessx/repo/infra/domain-setup/.env` — domains, Caddy settings, and the bcrypt verifier
  - `~/.headlessx/repo/infra/domain-setup/Caddyfile` — refreshed from the protected template

## How this works

The Caddy container joins the same Docker network as the HeadlessX app stack.
The dashboard vhost requires Basic Auth, removes the browser's `Authorization`
header, and then proxies to `web:3000`. The API vhost proxies to `api:8000`
without Basic Auth because protected API routes already require `x-api-key`.

TLS is handled automatically by Caddy. The separate dashboard password is
never the dashboard-internal API key and never an API or MCP client key.

## Current Docker Flow

CLI-first production flow:

```bash
headlessx init --mode production --api-domain api.example.com --web-domain dashboard.example.com --caddy-email ops@example.com
headlessx start
headlessx status
headlessx doctor
```

The CLI masked-prompts for and confirms the dashboard password. It gives the
plaintext only to `caddy hash-password` over stdin and saves only the bcrypt
verifier. `headlessx init update` adds this boundary to existing production
installs; unattended updates fail closed until
`--dashboard-password-hash <bcrypt>` is provided.
Restart immediately after the update so a running legacy Caddy container loads
the protected configuration.

The CLI clones the owner fork into `~/.headlessx/repo`, creates private app
credential sources under `~/.headlessx/repo/infra/docker/secrets`, keeps the
core Compose `.env` free of fixed credentials, writes the domain settings and
bcrypt verifier to a user-private domain `.env`, and starts the app stack
before the domain layer. Production app containers do not fall back to
environment values for their fixed credentials.

Manual flow from a repository checkout:

1. Prepare and start the core stack using [`../docker`](../docker) and the
   fixed-file procedure in [`../../docs/setup-guide.md`](../../docs/setup-guide.md)
2. Copy `.env.example` to `.env` in this directory
3. Fill in the domains, email, and dashboard username
4. Generate a bcrypt verifier with the command below and place the verifier,
   single-quoted, in `HEADLESSX_DASHBOARD_PASSWORD_HASH`
5. Copy `Caddyfile.template` to `Caddyfile`
6. Start the domain layer with Docker Compose

## Manual Example

```bash
cd infra/domain-setup
cp .env.example .env
docker run --rm -it --network none caddy:2.10-alpine \
  caddy hash-password --algorithm bcrypt
```

Enter the dashboard password only at Caddy's hidden prompt. Copy the resulting
hash into `.env` without copying the plaintext:

```env
HEADLESSX_DASHBOARD_PASSWORD_HASH='$2a$14$...'
```

Then:

```bash
chmod 0600 .env
cp Caddyfile.template Caddyfile
docker compose up -d
```

## Required values

Set these in `.env`:

- `HEADLESSX_WEB_DOMAIN`
- `HEADLESSX_API_DOMAIN`
- `CADDY_EMAIL`
- `HEADLESSX_DASHBOARD_USER`
- `HEADLESSX_DASHBOARD_PASSWORD_HASH` as a single-quoted bcrypt verifier

Compose refuses an empty verifier, and Caddy refuses an invalid one. Keep the
domain `.env` private because a bcrypt verifier permits offline password
guessing even though it cannot be used as the plaintext Basic Auth password.

You can also override:

- `HEADLESSX_WEB_UPSTREAM`
- `HEADLESSX_API_UPSTREAM`
- `HEADLESSX_DOCKER_NETWORK`

## Docker network

By default, this setup expects the HeadlessX app stack to already be running on:

```text
docker_headlessx-network
```

If your Compose project name differs, set `HEADLESSX_DOCKER_NETWORK` in `.env`.

The core stack's host mappings remain on `127.0.0.1`; Caddy reaches the web and
API services through this Docker network. Do not set a public
`HEADLESSX_HOST_BIND` in production, because it would bypass the dashboard
vhost.

## DNS

Before starting Caddy, point both domains to the server:

- dashboard domain -> server IP
- API domain -> server IP

Without valid DNS, automatic HTTPS will not complete.

The owner API-only production deployment does not use this Caddy layer. Its
direct root-owned credential and fixed Tailnet contract is documented in
[`../../docs/runbooks/headlessx.md`](../../docs/runbooks/headlessx.md).

## Notes

- this directory is for production/domain setup only
- the app stack still lives in `infra/docker`
- only ports `80` and `443` need public host bindings
- `headlessx stop` stops the Docker services started by the lifecycle commands
